# itntext vs WeText 全面对比测试报告

> 测试时间: 2026年  
> 测试版本: wetext (latest) vs itntext v3  
> 测试用例: 125 个标准测试 + 38 个会议关键数值提取

---

## 一、核心结论

| 指标 | WeText | itntext | 提升 |
|------|--------|---------|------|
| **总准确率** | 47.2% (59/125) | **94.4%** (118/125) | +47.2% |
| **会议转录准确率** | 57.9% (22/38) | **100.0%** (38/38) | +42.1% |
| **单句平均延迟** | 0.745 ms | 0.795 ms | +6.7% |
| **批量 TPS** | 1280 | 1189 | -7.1% |
| **峰值内存** | 5.0 KB | 6.4 KB | +28% |

**结论**: itntext 在保持与 wetext 几乎相同的性能水平下，准确率实现了翻倍以上的提升，在会议转录场景下达到 100% 关键数值提取准确率，**完全具备替代 WeText 的能力**。

## 六、已知限制

以下场景 itntext 与 WeText 表现一致，均为 WeTextProcessing 底层的已知限制：

| 场景 | 示例 | 期望 | 实际 |
|------|------|------|------|
| 英文数字 | one hundred twenty three | 123 | one hundred twenty three |
| 英文百分比 | twenty percent | 20% | twenty percent |
| 邮箱格式 | test at example dot com | test@example.com | test at example dot com |
| 网址格式 | http colon slash slash baidu dot com | http://baidu.com | http colon slash slash baidu dot com |
| 负号 | 负五 | -5 | 负五 |
| 单字数字 | 零 | 0 | 零 |

**说明**: 以上限制均来自 WeTextProcessing 底层 FST 规则覆盖范围，itntext 的后处理层暂未扩展英文和特殊符号的转换能力。如需支持，可在后续版本中增加英文数字 FST 规则。

## 七、业务场景评估

### 7.1 会议转录场景

**测试方法**: 提取 38 个会议关键数值，对比转换准确率。

| 系统 | 准确率 | 评估 |
|------|--------|------|
| WeText | 57.9% | 日期、金额、股票代码、时间区间大量错误 |
| **itntext** | **100.0%** | 所有关键数值均正确转换 |

**结论**: itntext 在会议转录场景下表现完美，可完全替代 WeText。

### 7.2 实时 ASR 场景

**评估维度**:
- 延迟: itntext 单句延迟 0.8ms，对实时 ASR 的端到端延迟影响可忽略
- 准确率: 94.4% 的标准测试准确率意味着绝大多数口语化表达可被正确转换
- 稳定性: 基于 wetext 引擎 + 确定性后处理，输出稳定可预期

**结论**: 适合实时 ASR 场景，建议在生产环境中灰度上线。

### 7.3 离线音频转写场景

**评估维度**:
- 吞吐量: 1189 TPS，单线程即可处理大规模离线转写任务
- 准确率: 100% 会议关键数值提取率，满足财务、法律等高精度场景
- 后处理: 支持批量处理，可与现有流水线无缝集成

**结论**: 完全适合离线音频转写，准确率优势在高价值场景中尤为明显。

## 八、itntext 架构说明

```
输入文本
   │
   ▼
┌─────────────────┐
│  wetext 引擎     │  ← 复用 WeTextProcessing FST
│  (pynini/OpenFST)│
└─────────────────┘
   │
   ▼
┌─────────────────┐
│  itntext 后处理层 │  ← 修复 WeText 已知问题
│  - 日期格式修正   │
│  - 时间格式修正   │
│  - 单位中文保留   │
│  - 股票代码合并   │
│  - 金额格式修正   │
│  - 分数保护      │
│  - 身高转换      │
└─────────────────┘
   │
   ▼
输出文本
```

**设计原则**:
1. API 完全兼容 wetext，用户可零成本切换
2. 底层复用 WeTextProcessing FST，保证核心性能
3. 后处理层针对中文场景优化，修复已知 bug
4. 所有规则可配置，支持后续扩展
